# npm 패키지 코딩 절차

## 사용 시점

이 저장소에서 기능 추가, 버그 수정, 공개 타입 수정 또는 빌드·배포 설정 변경을 수행할 때 사용한다. 문서-only 요청은 변경할 문서와 그 문서가 참조하는 소스·설정만 확인하고 전체 코드 검증은 생략할 수 있다.

## 필요한 입력

- 사용자 요청과 완료 조건
- 현재 작업 트리 상태 및 관련 구현·테스트·설정
- 지원 환경이나 호환성 요구가 있으면 해당 조건

먼저 [저장소 지침](../../../AGENTS.md)과 [프로젝트 구조](../../../docs/agents/project.md)를 읽는다.

## 진행 방식

한 에이전트가 분석 → 구현 → 검증 → 보고 순서로 수행한다. 작은 작업은 대화 안에서 결과를 정리한다. 여러 세션에 걸치거나 중단 후 인계가 필요한 작업만 [작업 기록 양식](templates/task.md)을 저장소 루트의 `_workspace/<작업명>/task.md`로 복사해 유지한다. 작업명은 경로로 안전한 짧은 영문·숫자·하이픈 조합을 사용한다. 서로 다른 작업 기록을 덮어쓰지 않는다.

### 1. 분석

`git status --short`를 읽고 기존 staged, unstaged, untracked 변경을 보존한다. 관련 소스·테스트·설정과 현재 공개 진입점, 패키지 배포 경로를 확인해 기대 동작, 수정 범위, 검증 방법을 정한다. `docs/agents/project.md`는 탐색 자료로 사용하고 현재 구현과 설정을 기준으로 검증한다. 요청의 핵심 동작이나 범위에 중요한 모호성이 있을 때만 사용자에게 질문한다.

### 2. 구현

- 공개 기능은 `src/`에 구현하고 `src/index.ts`의 내보내기를 확인한다.
- 타입 전용 API는 타입 재수출로 표시하고, 공개 타입 선언이 ESM/CJS 소비자 양쪽에서 해석되는지 확인한다.
- 기능 수정은 실제 API를 호출하는 테스트로 확인한다. 정상 입력, 의미 있는 경계값, 오류 처리 중 변경에 관련된 사례를 선택한다.
- 사용 방법이나 API가 바뀌면 README와 예제를 필요한 만큼 갱신한다.
- `dist/`는 생성물이며 직접 편집하지 않는다. 빌드가 `dist/*`를 정리할 수 있으므로 실행 전에 기존 작업 트리 변경을 확인한다.
- 배포 경로나 패키지 진입점 변경 시 `package.json`, Rollup 산출물, `npm pack --dry-run` 및 가능한 경우 소비자 설치 환경을 함께 점검한다.

결과는 코드와 필요한 테스트·사용 설명이다.

### 3. 검증과 검토

`AGENTS.md`의 타입·lint·테스트 명령 중 변경 범위를 검증하는 최소 명령을 실행한다. 빌드·공개 진입점 변경에는 Rollup과 `npm pack --dry-run`을 추가하고 소비자의 import/require 및 타입 해석을 가능한 환경에서 확인한다. 문서-only 변경은 링크·경로·명령·API 설명을 현재 파일에 대조하고 `git diff --check`로 확인한다.

실패하면 변경으로 인한 회귀, 기존 결함, 환경 오류를 증거로 구분한다. Watchman 접근 오류에는 Watchman 비활성화 테스트와 별도 Rollup 실행을 사용하고 이를 대체 검증으로 기록한다. MySQL 통합 테스트는 `MYSQL_INTEGRATION=1`과 테스트 전용 `.env` 데이터베이스를 요구하므로 운영 DB에는 실행하지 않는다. 원인이 불명확하면 실패 명령·오류·남은 확인을 보존하고 통과로 표시하지 않으며, 실패를 숨기기 위해 검사 설정을 완화하지 않는다.

마지막으로 diff를 읽어 요청 범위, 공개 API 누락, 생성물 수정, 기존 변경 훼손 여부를 검토한다. 결과는 검증 명령별 성공·실패·미실행 기록과 남은 위험이다.

### 4. 완료 또는 인계

변경 목적, 주요 파일, 검증 결과, 미확인 사항을 한글로 보고한다. 중단 시 작업 기록에 완료한 내용과 다음 행동을 남긴다. 기록을 읽는 다음 에이전트는 현재 작업 트리부터 다시 확인한다.
